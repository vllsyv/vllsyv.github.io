实战：手动测试一个Web项目

引言

在软件开发的生命周期中，测试是确保产品质量、满足业务需求的关键环节。对于业务逻辑复杂、资金流转敏感的金融科技（FinTech）类项目而言，一套严谨、全面的测试流程更是不可或缺。

本文将以一个典型的“供应链金融”项目中的“垫资代采”功能为例，从头到尾演示如何进行一次完整的手动测试。我们将从需求分析入手，逐步完成测试计划制定、测试用例设计、测试执行、缺陷管理，最终形成测试报告。

项目背景简介：
我们的被测系统是一个B2B供应链金融平台。其中“垫资代采”功能是核心业务：平台为下游采购商（客户）垫付资金，向上游供应商代采货物。货物先进入平台监管的仓库，客户随后分批付款赎货。流程涉及风控、支付、仓储等多个系统，逻辑复杂，对数据的准确性和流程的完整性要求极高。

核心业务流程：

  1. 风控前置：客户在下单前，需通过风控审核，获得授信额度和产品费率。
  2. 下单与支付：客户创建代采订单，并支付预付款（如总金额的30%）。
  3. 执行采购：平台向供应商支付尾款和税款，货物采购成功并入库。
  4. 赎回与发货：客户发起赎回申请（可分批），平台生成结算单，客户付款，付款成功后平台发货。

第一阶段：需求分析与评审

测试的第一步不是写用例，而是彻底理解我们要测试什么。

1. 获取需求文档（PRD）与设计稿
假设我们已经从产品经理那里获得了以下资料：

  • 《垫资代采功能需求说明书.v1.2》
  • 《用户交互设计（UI）原型》
  • 《系统接口（API）文档》

2. 分析需求，理解业务
作为测试人员，我们需要将需求转化为可测试的点。以“代采单下单”为例，我们需分析：

  • 前置条件：用户必须已登录且已完成企业认证；用户必须有有效的、足够的风控额度。
  • 业务规则：
    • 下单时，商品单价和费率是否从风控系统实时获取？还是采用缓存值？
    • 预付款金额 = （商品单价 * 数量 + 服务费）* 预付款比例（如30%）。
    • 服务费如何计算？（例如：货物总价 * 费率 * 占用天数）。
    • 是否存在商品数量/金额的限制？
  • 流程逻辑：
    • 点击“提交订单”，是直接创建订单，还是进入一个确认页面？
    • 创建订单后，下一步是直接跳转到支付，还是停留在订单详情页？
  • 数据一致性：
    • 订单详情页展示的数据（如金额、费率）是否与下单时计算的一致？
    • 订单状态流：待支付 -> 待付款（已付预付款） -> 待尾款 -> 待税款 -> 采购中 -> 已入库…

3. 提出疑问
在需求评审会议上，测试需要提出不清楚或存在矛盾的点。例如：

  • “如果用户在下单过程中，风控额度突然被调整或失效，系统如何处理？”
  • “支付预付款时，调用第三方支付接口失败，订单状态应回滚为‘待支付’还是变为‘支付失败’？”
  • “‘抄码’环节的具体操作流程是什么？系统如何确保发出的货物与客户赎回的货物批次一致？”

产出物：标注了大量测试点和疑问的需求文档。

第二阶段：制定测试计划

测试计划是测试工作的总纲，它定义了范围、策略、资源和进度。

《[项目名称]垫资代采功能测试计划》

1. 测试范围（In-Scope & Out-of-Scope）

  • 范围内：
    • 功能测试：代采单完整流程（创建、预支付、尾款支付、赎回、结算、发货）的正确性。
    • 接口测试：与风控系统、支付系统、仓储系统的接口联调。
    • UI测试：界面布局、文字、交互符合设计稿。
    • 数据测试：订单、支付、资金流水等数据计算的准确性。
    • 权限测试：不同角色（客户、运营、财务）的操作权限。
  • 范围外：
    • 性能测试、压力测试（本期不覆盖）。
    • 安全性测试（如渗透测试，由安全团队单独进行）。
    • 浏览器兼容性测试（本期优先保证Chrome浏览器）。

2. 测试策略

  • 功能测试：采用业务流程测试和功能分解测试相结合的方法。
    • 业务流程测试：覆盖主流程、备选流程和异常流程。
      • 主流程：正常客户，正常下单，正常支付，正常赎回。
      • 备选流程：客户分多次赎回、部分支付失败后重试。
      • 异常流程：额度不足、支付中断、重复提交订单。
  • 接口测试：使用Postman等工具构造请求，验证接口的请求/响应格式、状态码、业务状态、错误码。
  • 数据测试：针对金额计算，编写测试用例时需明确计算公式和预期结果，测试时与需求说明逐一核对。

3. 测试资源与环境

  • 测试环境：https://test-environment.example.com
  • 测试账号：
    • 客户A：已有额度 1,000,000元，费率 0.0005
    • 运营账号：用于审核、抄码等操作。
    • 财务账号：用于确认款项。
  • 依赖系统状态：需提前与风控、支付团队沟通，确保测试环境的相关系统服务可用。

4. 进度安排

阶段 任务 预计工期 开始日期 完成日期
第一阶段 测试分析与用例设计 3人日 2023-10-26 2023-10-28
第二阶段 测试用例评审与更新 1人日 2023-10-29 2023-10-29
第三阶段 第一轮测试执行 4人日 2023-10-30 2023-11-02
第四阶段 第二轮回归测试 2人日 2023-11-03 2023-11-04
第五阶段 测试报告与收尾 1人日 2023-11-05 2023-11-05

5. 风险与应对

  • 风险：依赖的支付接口不稳定。
  • 应对：提前协调支付团队提供技术支持；准备模拟工具（Mock）以备不时之需。

第三阶段：测试用例设计

测试用例是将测试计划转化为可执行操作的关键步骤。好的测试用例应具备清晰、可重复、覆盖全面等特点。我们将使用场景法和功能分解法来设计用例。

1. 业务流程分析（场景法）
首先，我们绘制核心的业务流程图，并据此设计主干场景的测试用例。

核心流程场景：

  1. 场景S1：成功完成一次完整代采和赎回
    • 用户登录 -> 创建代采单 -> 支付预付款 -> 系统支付尾款 -> 系统支付税款 -> 货物入库 -> 用户发起赎回 -> 运营抄码 -> 生成结算单 -> 用户付款 -> 运营发货 -> 订单完成。

备选/异常流程场景：
2. 场景S2：额度不足时尝试下单
* 用户登录 -> 创建代采单 -> 系统提示“额度不足，下单失败”。
3. 场景S3：支付预付款后，用户取消订单（ before 支付尾款）
* … -> 支付预付款 -> 用户在前台申请取消 -> 运营审核取消 -> 生成退款单 -> 退款至用户账户。
4. 场景S4：分多次赎回货物
* … -> 货物入库 -> 用户第一次赎回（部分数量）-> … -> 发货 -> 用户第二次赎回（剩余数量）-> … -> 发货。

3. 测试数据准备
设计用例的同时，就要考虑所需的数据。例如：

  • 测试账号：test_company@example.com (密码：xxx)
  • 测试商品：商品ID SKU-001，名称“测试专用铜材”，供应商“测试供应商A”。
  • 风控数据：确保该测试账号的额度为1,000,000，费率为0.0005。

产出物：详尽的《测试用例》Excel或XMind思维导图文件。

第四阶段：测试执行与缺陷报告

环境准备好后，我们开始按计划执行测试用例。

1. 执行测试

  • 按照测试用例的步骤一步步操作。
  • 仔细比对预期结果和实际结果。
  • 对于所有不符合预期的地方，都要记录为缺陷（Bug）。

2. 提交缺陷报告（Bug Report）
一份清晰、准确的缺陷报告能极大提升开发人员的修复效率。缺陷报告应包含以下要素：

标题：【模块】【操作】现象简要描述
示例：【代采下单】【计算费用】商品数量输入小数，页面JS报错，未弹出友好提示

缺陷描述：

  • 环境：测试环境 (Chrome 浏览器 118.0)
  • 前提条件：用户已登录且风控额度有效。
  • 操作步骤：
    1. 进入“创建代采单”页面。
    2. 在“商品数量”输入框中输入 10.5。
    3. 点击“计算总价”按钮。
  • 预期结果：系统应弹出提示“请输入有效的正整数”，且不进行费用计算。
  • 实际结果：页面控制台出现JavaScript Uncaught TypeError错误，页面UI卡死，无任何提示。
  • 附件：(非常重要!)
    • 截图：展示输入框的值和控制台报错信息。
    • 日志：如果有，提供网络请求（Network）的报错日志。
    • 屏幕录制：对于复杂问题，录屏是最好的说明。

严重程度 (Severity)：S2-Major (主要功能受影响，阻塞后续测试)
优先级 (Priority)：P1-High (需要尽快修复)

3. 缺陷跟踪与管理

  • 使用Jira、禅道、TAPD等工具管理缺陷。
  • 测试人员需要定期跟踪已提交Bug的状态（如“已打开”、“已修复”、“待复测”、“已关闭”）。
  • 对开发修复后的Bug进行回归测试，验证通过后关闭。

好的，我们进入最后的部分。

第五阶段：测试报告与总结

测试执行完成后，需要将测试过程、结果和最终结论进行汇总，生成测试报告，为项目上线提供决策依据。

《垫资代采功能V1.0测试报告》

1. 测试概要

  • 项目名称：供应链金融平台
  • 测试版本：V1.0.0
  • 测试周期：2023-10-26 至 2023-11-05
  • 测试人员：XXX, YYY
  • 测试环境：测试环境 (https://test-env.example.com)
  • 测试目标：验证“垫资代采”核心业务流程的正确性、稳定性和数据准确性。

2. 测试范围与执行情况

  • 用例执行统计：

    测试类型 计划用例数 执行用例数 通过 失败 阻塞 通过率
    业务流程测试 35 35 33 2 0 94.3%
    功能特性测试 120 120 118 2 0 98.3%
    接口测试 25 25 25 0 0 100%
    总计 180 180 176 4 0 97.8%

  • 缺陷统计：

  • 严重级别 致命(S1) 严重(S2) 一般(S3) 轻微(S4) 总计
    Bug数量 0 2 2 0 4

状态分布：已修复：4个，已关闭：4个。

3. 测试结果分析

  • 通过率分析：本次测试用例通过率为97.8%，所有计划测试内容均已执行完毕。剩余4个缺陷已全部修复并经过回归测试验证通过。
  • 缺陷分析：
    • 发现的2个严重(S2)缺陷分别为：①支付回调处理不当导致订单状态未更新；②赎回结算单金额计算错误（使用了错误的天数）。这两个缺陷均涉及核心业务和资金逻辑，修复后已验证。
    • 缺陷主要集中在“支付状态管理”和“费用计算”模块，建议开发团队在此后的开发中加强此类业务的代码审查和单元测试。
  • 风险评估：
    • 剩余风险：目前已知问题已全部修复，无剩余高风险问题。存在一个低风险问题：订单列表页在极端网络条件下加载可能稍慢，但不影响功能正确性，建议V1.1版本优化。
    • 上线建议：通过。当前版本功能稳定，核心业务流程畅通，数据计算准确，已达到上线标准。

现代测试管理：利用工具自动化报告

在实战中，我们无需手动统计大量数据。专业的测试管理工具（如禅道）可以自动追踪用例执行结果和缺陷状态，并生成可视化的统计图表。测试工程师的核心价值由此从“数据统计员”转变为“质量分析师”——我们将工具自动生成的数据作为输入，结合对业务的深刻理解，进行风险分析和做出是否上线的最终决策。这极大地提升了测试报告的产出效率和专业性。

总结

手动测试并非“点点点”，而是一套严谨的工程方法。它要求测试人员不仅要有“找茬”的细心
