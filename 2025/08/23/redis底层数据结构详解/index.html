动态简单字符串SDS

1. 概述

Redis中的字符串是一种最基本的数据结构，它可以存储任意长度的字符串。

底层设计实现中，并不是用c语言的数组直接存储字符串，而是在外套了一层结构体。
称之为Simple Dynamic String，简称SDS，SDS不只是为了存储字符串，也可以存储二进制信息，如图片等

3. 优点

这样可以拥有如下优点

  1. 由于内部使用的数组，本质上和c语言的字符串是一样的，都是用’\0’作为结尾，所以字符串操作和c语言的数组操作一样简单，并且可以使用原生字符串的相关函数
  2. 获取字符串的长度的复杂度由O(N) 降低为O(1)。
    原先需要遍历数组，直到找到’\0’为止，现在只需要访问len属性
    这确保了获取字符串长度的工作不会成为redis的性能瓶颈
  3. 杜绝缓冲区溢出
    如存在连续分配的两个数组，s1=[Redis],s2=[MongoDB],若使用函数strcat为数组s1追加内容
    而没有提前分配内存空间，则会导致执行strcat(s1, ‘ OK’)后，内存出现[Redis OkngoDB].
    而使用SDS的API则不会出现这种问题，在API中会先检查空间是否满足，如果不满足则进行扩容，这样无需手动修改，可以避免遗漏而导致错误。
  4. 减少内存重分配次数
    由于存在缓冲区，这边类似java的List，会自动扩容，并且预留一部分空间，防止下次修改还需要扩容，重新分配内存
    • 扩容策略：和java不同，若空间小于1MB，每次分配的空间=2N，也就是len=free，预留一倍空间
      若空间已经大于1MB，则每次增加1MB的free空间
    • 释放策略：惰性释放，也就是默认情况下不会释放，但提供了API接口可以手动释放，或者在内存回收时进行释放
  5. 升级后的优化点
    • 节省头部开销：对于一个只有 1 字节的字符串，Redis 会选择 sdshdr8，其头部总开销仅为 len(1) + alloc(1) + flags(1) = 3 字节，远比旧版本的 8/16 字节要小。
    • 使用 attribute ((packed))：告诉编译器取消结构体的内存对齐优化，虽然可能降低一点点 CPU 访问速度，但能节省每一个字节，这对于内存数据库来说是值得的。
      • attribute ((packed))：取消内存对齐优化，CPU 并非一次只从内存中读取一个字节。它通常以“字”（word）为单位进行读取（例如，64 位系统一次可读取 8 个字节）。为了提高访问速度，计算机系统会要求数据在内存中的起始地址必须是某个值（通常是其自身大小）的整数倍。 例如，一个 uint16_t（2 字节）的变量，其起始地址最好是 2 的倍数。一个 uint32_t（4 字节）的变量，其起始地址最好是 4 的倍数。 如果编译器不做任何处理，直接按照我们结构体定义的顺序排列变量，可能会为了满足对齐规则而在成员之间插入“空洞”（padding bytes）。
      • 当取消对齐优化之后，这些空洞就都不会出现，这样可以节省大量碎片内存，对redis这种内存型数据库是非常有利的
    • 使用 flags 字段标识类型：程序可以通过 flags & SDS_TYPE_MASK 来快速判断当前 SDS 头的类型，从而知道如何解析它。
      • 所有类型的 SDS 头部都有一个 flags 字段，并且这个字段总是位于 SDS 内存布局的相同位置（具体来说，是 buf 指针向前偏移 1 字节的位置）。
      • SDS_TYPE_MASK=7，也就是00000111
      • int type = flags & SDS_TYPE_MASK;由于flag只用到了3位，所以这样就可以快速获得类型
  6. 二进制安全
    • C语言的字符串固定由‘/0’作为结尾，所以无法存储图片、音频、视频等二进制信息，因为这些信息中可能随时会带有‘/0’，这样会导致字符串截断，从而导致数据丢失。
    • SDS结构体由于使用的是len属性来标识结尾，所以可以存储任意二进制信息，并且不会出现截断问题。

链表

0. 概述

链表是一种常见的数据结构，它可以实现动态数组的功能，但是链表在插入和删除元素时性能会低于动态数组。
c语言中并没有链表相关的数据结构，所以redis构建了自己的链表实现。

1. Redis链表类型

  • 在早期版本中，链表会根据配置的阈值，选择双向链表(linkedlist)或者压缩列表（ziplist）
  • 在Redis 3.2 以后，统一使用快速列表（quicklist）来进行维护

3. 压缩列表（ziplist）

  • ziplist实际上是一种数组结构（连续内存分配），而非传统链表
  • 他是为短小的、不可变的列表提供极致的内存效率。它是一块连续的内存，没有任何指针开销。
  • 压缩列表结构如下
    • ZLBYTES (4字节)：记录整个 ziplist 占用的内存总字节数。
    • ZLTail (4字节)：记录到最后一个 Entry 的偏移量，方便快速进行 RPUSH 或 RPOP。
    • ZLLEN (2字节)：记录 Entry 的个数。但如果数量超过 2^16-1，这个值就无效了，需要遍历整个列表才能计数。
    • Entry (不定长)：存储实际数据的单元，这是 ziplist 的精髓所在。
    • ZLEND (1字节)：一个特殊的标记（值255），表示 ziplist 的结束。
  • 其中Entry的结构如下
    • Previous entry length (前一个条目的长度)：
      • 长度：1 字节或 5 字节。
      • 如果前一个 Entry 的长度 < 254 字节，则本字段用 1 字节存储。
      • 如果前一个 Entry 的长度 >= 254 字节，则本字段用 5 字节：第一个字节固定为 0xFE（254），后 4 字节存储实际长度。
      • 作用：支持从后向前遍历。知道了当前 Entry 的起始地址，减去这个值，就能找到前一个 Entry。
    • Encoding (编码)：
      • 长度：1、2 或 5 字节。
      • 这个字段非常智能，它同时记录了内容的长度和类型（是整数还是字符串）。
        • 00xxxxxx 1 byte 长度 ≤ 63 的字符串。 后 6 位直接表示字符串的长度（0 to 63）。这是最常用的情况。
        • 01xxxxxxxxxxxxxx 2 bytes 长度 ≤ 16383 的字符串。 后 14 位（2字节的后14位）用来表示长度。大端序存储。
        • 10xxxxxxxxxxxxxx (共4字节) 5 bytes 长度 > 16383 的字符串。 第 1 个字节的后 6 位无效。后续 4 个字节（一个32位无符号整数）用来表示长度。大端序存储。
        • 11xxxxxx 存储整数
          • 11000000 存储int16_t (2 bytes)的整数
          • 11010000 存储int32_t (4 bytes)的整数
          • 11100000 存储int64_t (8 bytes)的整数
          • 1111xxxx
            • 1111xxxx (xxxx从0001到1101), 特殊情况，这种情况内容就是后4位数,内嵌在encoding中
            • 11110000 24位整数标记，数据存储在后面3个字节
            • 11111110 8位整数标记，数据存储在后面1个字节
            • 11111111 ziplist，结束标记
    • Actual Data (实际数据)：
      • 存储真正的数据，比如 “hello”, 42 等。

4. 快速列表（quicklist）

  • Quicklist 是一个由 QuicklistNode 组成的双向链表
  • 设计目标： 解决 ziplist 和 linkedlist 的各自缺陷。它想要：大部分情况下拥有 ziplist 的内存效率，同时在修改操作时保持 linkedlist 的性能可控性。
  • 它的核心思想是：“化整为零”。不再使用一个巨大的 ziplist，而是将一个大列表拆分成许多个小 ziplist，再用一个双向链表把这些小 ziplist 连接起来。
  • 结构如下
  • 结构示意图如下
 - 内存效率：假设一个 quicklistNode 里的 ziplist 包含 8 个元素。那么这 8 个元素才共享一对 prev/next 指针（16字节），而不是每个元素都背负一对指针。元数据开销被平均了，内存利用率接近 ziplist。
 - 性能可控： 两端操作（LPUSH, RPOP）：通常在头/尾节点的 ziplist 上进行，速度极快。如果头节点 ziplist 没满，就直接往里加；如果满了，就新建一个 quicklistNode 节点。 
 - 中间操作：即使在某个 ziplist 中间插入数据触发了“连锁更新”，也只会发生在那一个小的 ziplist 内部，而不会像巨型的单一 ziplist 那样导致灾难性的全列表更新。这将最坏情况下的性能影响限制在了一个很小的、可接受的范围内。

字典

Redis 的字典是一个非常核心的数据结构，它不仅是 HASH 类型键的底层实现之一，还用于存储 Redis 的所有键值对（Key-Value Pair）、过期时间、数据库信息等。因此，其性能和稳定性直接关系到 Redis 的整体表现。

0. 基础概念澄清

2. 数据结构详细说明

字典 (dict)：这是整个字典的顶层结构。

  • dict结构是整个字典的顶层结构

哈希表 (dictht)：这才是真正存储数据的地方。

  • table：是一个数组，数组的每个元素是一个指向 dictEntry 的指针（可以理解为链表的头指针）。
  • sizemask：和键的哈希值做 与 操作，来决定键应该落在哪个桶里，这比取模运算更快。index = hash & sizemask。.

哈希表节点 (dictEntry)：存储具体的键值对。

  • next 指针用于将哈希到同一个桶的多个节点连接起来，解决哈希冲突。

3. 数据的插入和删除过程

  • 数据插入过程
    1. 计算键的哈希值：hash = dict->type->hashFunction(key)。
    2. 根据 rehashidx 判断是否正在进行 Rehash：
      • 如果没有 Rehash (rehashidx == -1)，使用 ht[0] 计算索引：index = hash & ht[0].sizemask。
      • 如果正在 Rehash (rehashidx != -1)，则同时使用 ht[0] 和 ht[1]。首先在 ht[0] 中查找，如果没找到，再去 ht[1] 中查找。插入操作则直接写入 ht[1]。
    3. 遍历找到的桶对应的链表，对比键（使用 dict->type->keyCompare）。
    4. 根据操作是查找还是插入进行后续处理。

4. 哈希值的计算以及哈希算法的选择

  1. 计算原始哈希值：使用一个哈希函数，将任意长度的键（key）转换成一个唯一的、固定长度的整数值（如 uint64_t）。
    简化代码如下
  • Redis 并非始终使用同一个哈希函数，其选择策略在不同版本中有演进，核心目的是在性能与安全性之间取得平衡。
  • Redis 4.0 及之前：单一的 MurmurHash2
    • 算法：hash = murmurhash2(key, len)
      • 特点：
        • 高性能：非加密型哈希函数，计算速度非常快。
        • 分布均匀：产生的哈希值随机分布性（avalanche effect - 雪崩效应）很好，能有效避免一般情况下的哈希冲突。
        • 安全性问题：MurmurHash2 及其早期版本存在一个种子可预测性漏洞。如果攻击者知道了 Redis 实例使用的哈希种子，就可以精心构造大量具有相同哈希值的键（哈希碰撞攻击）。这会导致哈希表退化成链表，查询操作从 O(1) 恶化为 O(n)，从而消耗大量 CPU，引发服务拒绝（DoS）。
  • Redis 6.0 及之后：动态哈希算法选择
    • 为了解决上述安全问题，Redis 6.0 引入了更智能的策略：
      1. 使用随机化的哈希种子（Hash Seed）
        Redis 实例在启动时，会生成一个随机的哈希种子（dictGenHashFunction 的 seed 参数），而不是一个固定值。这使得攻击者无法预测哈希函数的输出。
      2. 根据键的长度动态选择算法
        这是更核心的优化。策略如下：
        • 对于短键（长度 <= HASH_USING_SEED_LENGTH_THRESHOLD，默认 1024 字节）：
          • 算法：仍使用 MurmurHash2。
          • 原因：性能极高。对于绝大多数场景（键名通常很短，如 “user:1000:name”），能保证最佳性能。由于种子是随机的，短键情况下遭遇碰撞攻击的难度大大增加。
        • 对于长键（长度 > HASH_USING_SEED_LENGTH_THRESHOLD，默认 1024 字节）：
          • 算法：切换为 SipHash。
          • 原因：SipHash 是一种加密强度的伪随机函数。即使攻击者知道种子，想构造出碰撞的键在计算上也是不可行的（需要极高的成本），从而彻底免疫哈希碰撞攻击。虽然它的计算速度比 MurmurHash2 慢，但对于长键（本身就不常见），为了安全牺牲一点性能是值得的。

    1. 扰动与混合（Redis 6.0+）：为了安全，将这个原始哈希值进行再次混合。
      在某些内部路径中，Redis 会对哈希值 h 进行一个额外的“扰动”操作，例如 h ^ (h >> 46)，目的是让哈希值的低位更加随机，进一步减少冲突的概率。但这个操作不是每次都必须的，核心的哈希值已经由第一步的高质量算法保证了。

    2. 计算索引位置：利用哈希表的 sizemask，将这个整数值映射到哈希表数组的一个具体下标上。
      得到最终的哈希值 h（一个 64 位无符号整数）后，并不是用它直接作为数组下标，因为数组大小 size 远小于 2^64。

      Redis 使用了一个非常高效的方法：

      1. 确保哈希表的大小 size 永远是 2 的 n 次方（例如 4, 8, 16, 32, …）。
      2. 那么 sizemask 就永远是 size - 1（二进制表示为一串连续的 1，例如 size=8, sizemask=7，二进制为 0111）。
      3. 将哈希值 h 和 sizemask 进行按位与（&） 操作。

      举个例子：

      • 哈希表大小 size = 16
      • sizemask = size - 1 = 15 (二进制 00001111)
      • 假设一个键的哈希值 h = 12345 (二进制 0011000000111001)
      • 计算索引：index = 12345 & 15
        • 0011000000111001 (h = 12345)
        • & 0000000000001111 (sizemask = 15)
        • = 0000000000001001 (index = 9)
      • 为什么这样做？
        • 性能极高：按位与(&) 操作是 CPU 最基本的指令，速度远快于 取模运算(%)。
        • 效果等价：因为 sizemask 是连续的 1，所以 h & sizemask 的结果等价于 h % size，但确保了结果一定在 [0, size-1] 的范围内。
